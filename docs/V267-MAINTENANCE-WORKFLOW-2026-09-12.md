# استكمال دورة الصيانة الدورية — 12 سبتمبر 2026

الحالة: تنفيذ برمجي واختبار PostgreSQL معزول، ولم يطبّق هذا التحديث على قاعدة مستضافة أو الإنتاج. لا يغلق هذا الدليل جميع بنود الصيانة أو البنود الـ155.

## الفجوة المثبتة

كانت الخطة تحتفظ بحقل عقد المورد دون واجهة لاختياره أو تحقق يربطه بعقار الخطة وموعدها. وكانت المهام تُنشأ دون واجهة تكليف جهة منفذة أو بدء تنفيذ أو إلغاء مسبب. تغيير عقار خطة موجودة كان يفحص صلاحية العقار الجديد دون فحص العقار الأصلي، كما أتاح رد القائمة لموظف الصيانة تنبيهات عقود إيجار لا تخص عمله.

أُجري اختبار القبول نفسه على المصدر السابق، دون التحديث الجديد، وفشل فعليًا بـ`INVALID_CONTRACT_ACCEPTED`: قَبِل ربط خطة عقار بعقد مورد عقار آخر. بعد تطبيق التحديث نجح الاختبار الكامل.

## التنفيذ

- [واجهة الخطط والمهام](../src/v267/pages/maintenance-plans.js): اختيار عقد المورد الموافق للعقار، تعديل الخطة وإيقافها دون حذفها، منع إنشاء مهمة ثانية لنفس الموعد، تكليف المورد، بدء التنفيذ، توثيق الإنجاز، وإلغاء مسبب. تظهر الجهة المنفذة وتاريخ التكليف والحالة بالعربية. اختيار المورد يقتصر على مورد العقد عند ربطه بالخطة.
- [تحديث قاعدة البيانات](../staging-database/sql/maintenance-workflow.sql): ملف إضافي قابل لإعادة التطبيق بعد `maintenance-automation.sql`. يضيف حقول التكليف والبدء والإلغاء دون تغيير البيانات السابقة. يبقي اسم RPC الحالي `aqari_maintenance_plans` بواجهة عامة `SECURITY INVOKER` ومساعد خاص محمي بالصلاحيات والتحقق الثنائي للحسابات الحساسة.
- صلاحيات العقار الأصلي تُفحص قبل تعديل الخطة، ولا يمكن نقل خطة محفوظة إلى عقار آخر. لا يتغير الموعد أو التكرار أو عقد المورد أثناء وجود مهمة مفتوحة.
- يُرفض عقد المورد غير المعتمد، أو خارج العقار أو الفترة، والمورد الموقوف، وتعارض جهة التكليف مع العقد. ربط عقد بالخطة يكلّف مورده تلقائيًا عند توليد المهمة.
- يجب بدء المهمة قبل اعتماد إنجازها. الاعتماد يتطلب صلاحية قراءة الوثائق بالإضافة إلى الصيانة. لا تُكشف عناوين أو أرقام الوثائق لمسؤول صيانة محروم من قراءة الوثائق. مستند الإنجاز ومراجع الصور يجب أن تكون ملفات محفوظة ومتحققًا منها لنفس العقار، ويُرفض مرجع من عقار آخر، كما يُرفض PDF وDOCX في موضع صورة الإنجاز؛ للصورة اختيار مستقل بواجهة الاعتماد. الإكمال يحدد الموعد التالي من موعد المهمة وتكرار الخطة، مرة واحدة.
- حفظ التكليف والبدء والإلغاء والتعديلات يسجل الجهة الفاعلة والأثر قبل العملية وبعدها. جميع العمليات تتطلب رقم مراجعة حديثًا.
- كل حفظ يتبعه طلب قائمة مستقل للتحقق من الهوية والمراجعة والحقول المتغيرة. القراءة المختلفة أو غير المؤكدة تمنع إعادة الكتابة حتى تحديث السجل ومراجعة المحفوظ.
- مسؤول الصيانة المحدود يكلّف ويبدأ التنفيذ، ويتولى اعتماد الإنجاز مدير مخول بالمستندات؛ هذا ليس إثباتًا لدورة اعتماد كاملة لحساب صيانة محدود. تُحجب واجهة الاعتماد عند غياب `can_complete`. موظف الصيانة يرى خطط ومهام وعقود موردي العقارات المخولة له وتنبيهات الصيانة ذات الصلة. لا يحصل عبر هذه الصفحة على تنبيهات عقود الإيجار أو سجل تجهيز الإدارة. سحب تكليف العقار يسري على القراءة والكتابة التالية مباشرة.
- إذا كانت قاعدة النسخة أقدم من التحديث، لا تعرض الواجهة أدوات إدارة غير متاحة فيها.

## أدلة الاختبار

[اختبار PostgreSQL السلوكي](../staging-database/tests/maintenance_workflow.sql) نجح على قاعدة PGlite مستعادة من كتالوج المخطط المعتمد، دون اتصال بقاعدة مستضافة. طُبق ملف التحديث مرتين بنجاح قبل الاختبار. جميع المستخدمين والعقارات والعقود والمهام وبيانات Storage الاختبارية اصطناعية، وتُرجع المعاملة جميع كتاباتها.

الدورة المثبتة: خطة مرتبطة بعقد → توليد مهمة وتكليف المورد → بدء → رفض دليل من عقار آخر → إنجاز بتكلفة `25.125` → إعادة قراءة الموعد التالي `2026-10-12` → توليد التكرار الثاني → إلغاء مسبب → إيقاف الخطة، مع بقاء المهمتين في التاريخ. اختُبر أيضًا التكليف اليدوي ورفض المورد الموقوف، المراجعة القديمة، التكرار، بدء مهمة دون تكليف، وإنجازها قبل البدء.

اختُبرت صلاحيات المدير ومسؤول الصيانة، عقار آخر في مساحة العمل ومساحة عمل أخرى، سحب تكليف العقار، إخفاء تنبيهات عقود الإيجار، منع القراءة المباشرة للجداول الخاصة والوصول المجهول ورفض كتابة حساب حساس دون AAL2.

[اختبارات واجهة سلوكية](../tests/v267-maintenance-workflow.test.cjs) تنفذ الوحدة الفعلية في DOM معزول وتغطي مطابقة جميع حقول الخطة بعد الحفظ، اختلاف المورد في إعادة القراءة، منع تكرار كتابة غير مؤكدة، استعادة السجل، إيقاف الخطة دون حذفها، قفل العقار أثناء التعديل، عرض المورد الموافق للعقد، رفض التاريخ غير الصالح، إخفاء أدوات الكتابة للقارئ، والتخلص من البيانات عند إغلاق الصفحة.

نتيجة اختبارات الوحدة: **13 نجاحًا، صفر فشل أو تخطٍ**، تشمل الاختبارات السلوكية الخمسة الجديدة وثمانية اختبارات موجودة.

لإعادة فحص الوحدة:

```sh
node --test tests/v267-maintenance-workflow.test.cjs tests/v267-maintenance-plans.test.cjs tests/v267-maintenance-automation.test.cjs
```

اختبار SQL يستعمل المشغل الموجود `staging-database/local-test/run-isolated.mjs` بترتيب الملفات: `mfa-enforcement.sql` ثم `staff-property-scope.sql` ثم `financial-register.sql` ثم `operations-completion.sql` ثم `operations-register.sql` ثم `maintenance-automation.sql` ثم `maintenance-workflow.sql` مرتين ثم `tests/maintenance_workflow.sql`.

## حدود الدليل والربط المطلوب

يمثل تقدمًا محددًا في البنود 84 و85 وجزء من ربط المورد والعقد، وليس اكتمال 83 أو 86 أو 89 أو 142 أو 143. لم يُختبر إسناد المورد أو المسح على iPhone فعلي، ولا رفع/تنزيل ملف عبر Storage مستضاف. بيانات الملفات في SQL اصطناعية للتحقق من قواعد الربط، وليست إثباتًا لرفع صورة فعلية.

لم يُربط هذا المسار بعد بطلب صيانة المستأجر أو أمر شغل وفاتورة مالية، ولا يسجل تكلفة المهمة تلقائيًا كمصروف معتمد. لم تُفعّل جدولة أو رسائل مزود خارجي، ولم يتم نشر أو تفعيل تحديث قاعدة مستضافة. يلزم إدراج التحديث واختباره في ترتيب SQL الخاص بالمعاينة، ثم قبول استخدام فعلي قبل أي إعلان جاهزية شاملة.
