# عزل الشريك حسب العقار — Staging، ٩ سبتمبر ٢٠٢٦

التنفيذ على PR #69 فقط. ليس اعتمادًا نهائيًا للمنصة. لا تغيير لـ Production أو myaqari.com أو V266.

## الاستخدام

1. يفتح المدير «المزيد ← صلاحيات الشركاء حسب العقار» ويحدد البريد واسم الشريك والعقار وحالة الوصول وسبب التعديل.
2. تحفظ العملية الصلاحية مع رقم مراجعة وسجل تدقيق، ثم تقرأها الواجهة مرة أخرى. إذا لم تتأكد النتيجة، يلزم تحديث الصلاحيات قبل إعادة الحفظ.
3. يدخل الشريك من رابط «دخول الشريك» في صفحة الدخول، أو من `partner.html`. إذا لم ينشئ الحساب بعد، يستخدم نفس البريد الذي أجازه المدير. لا يرسل منح الصلاحية دعوة تلقائية.
4. يرجع رابط تأكيد البريد إلى صفحة الدخول المعتمدة الحالية؛ يختار المستخدم دخول الشريك ويسجل الدخول بعد التأكيد. لم تُغيّر إعدادات عناوين الرجوع أو SMTP.
5. تعرض البوابة العقارات المصرح بها فقط، مع عدد الوحدات والعقود المسودة والوصول والمقبوضات المسجلة حسب تاريخ الدفع في الشهر المختار. المبالغ ليست صافي الربح أو توزيع حصة الشريك ولا تؤكد اكتمال البيانات.

## حدود الصلاحيات

- صلاحيات العقارات محفوظة في جدول `private.aqari_partner_access` مع RLS ومنع الوصول المباشر. لا تُقرأ من بيانات مستخدم قابلة للتعديل ولا من اختيار الواجهة.
- حساب الشريك مستقل عن حساب الموظف العام في مساحة العمل نفسها. إنشاء حساب مأذون مسبقًا لا ينشئ عضوية موظف. وتُرفض إضافة العضوية لاحقًا حتى لو سُحب الوصول إلى العقار.
- الدوال العامة تعمل بصلاحيات المستدعي وتستدعي وظائف محددة في المخطط الخاص. تتحقق وظيفة الملخص من هوية المستخدم وتأكيد البريد وتطابق البريد الحالي مع المنحة، ثم تربط العقار بمساحة عمله المصرح بها.
- لا تعرض البوابة ملفات المستأجرين أو أرقام هوياتهم أو مستنداتهم أو كائنات JSON الأصلية. لا تتيح تعديل بيانات الأعمال أو تنزيل الوصول الخاصة بهم.
- التفويض صالح للقراءة المحددة فقط؛ لا يُغيّر سجل الحصص المالية الحالي ولا يوزع مبالغ تلقائيًا. سحب الوصول يسري على الطلب التالي، ولا يعتمد على انتظار تجديد JWT.
- تحفظ جلسة الشريك بمفتاح منفصل عن جلسة الإدارة والمستأجر. تغيير الحساب والخروج وإخفاء الصفحة يمسح البيانات والمدخلات الخاصة، ويلغي القراءات الجارية. تشمل مهلة القراءة انتظار SDK واستجابة RPC والتحقق اللاحق من هوية الجلسة.

## دليل الفحص

نجح `staging-database/tests/partner_property_access.sql` مباشرة في قاعدة Staging:

- شريكان وعقاران؛ كل حساب يرى عقاره ويُرفض طلب عقار الآخر.
- مبالغ ١٠٠ و٩٠٠ لعقارين مختلفين، ومبلغ ٣٠٠ في الشهر السابق؛ ملخص الشريك الأول أعاد ١٠٠ ووصلًا واحدًا فقط.
- منع الجداول الخام وحزمة البيانات القديمة وقائمة المنح الإدارية والمنح الذاتية.
- رفض تعديل منحة برقم مراجعة قديم ورفض العقار غير الموجود؛ التحقق من سجل التدقيق.
- سحب الوصول، رفض الحساب غير المؤكد والطلب المجهول، ومنع ترقية الشريك إلى عضوية موظف عامة.
- استمرار إنشاء حساب المستأجر المعتمد ورفض البريد غير المصرح به. ونجح اختبار `workspace_controls.sql` مجددًا، بما فيه إنشاء حسابَي مدير ومحاسب وصلاحياتهما.
- عشرة اختبارات Node جديدة لهوية الجلسة والعقار والشهر، إلغاء الاستجابات القديمة، الخروج، تبديل الحساب، والمهلة. المجموعة المحلية الكاملة: **٥٣٢ ناجحة، صفر فشل أو تخطي**.

كل بيانات SQL اصطناعية وانتهت بـ ROLLBACK. القراءة اللاحقة أكدت: حساب Auth واحد، عقار واحد، ٤٢ وحدة، ٤١ مستأجرًا، ٤٢ عقدًا، صفر دفعات ومستندات وحسابات بوابة ومنح شريك باقية. هذا لا يمثل دخولًا بحساب شريك فعلي في المتصفح.

تبقى فحوص CI المتوقفة قبل بدء التنفيذ والفحص بحساب فعلي وعلى أجهزة المستخدم شروطًا مفتوحة. لا تُنسب إليها نتائج اختبارات SQL أو Node. يسجل وصف PR حالة نشر المعاينة والفحص الحي بعد هذا التعديل.
