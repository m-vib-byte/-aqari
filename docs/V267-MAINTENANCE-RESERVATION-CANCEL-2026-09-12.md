# إلغاء حجوزات مرفقات الصيانة غير المكتملة — V267

## النطاق

هذا الإصلاح يعالج فجوة حجوزات الملفات التي بدأ المستخدم رفعها ثم فقد الأصل أو غادر الصفحة قبل اكتمال الحفظ. الحجز غير المكتمل كان يبقى محتسبًا ضمن حد ثمانية مرفقات، وقد يمنع رفع ملف جديد رغم عدم وجود أصل محفوظ نهائيًا.

## التنفيذ الحالي

- تعيد قراءة قائمة المرفقات الحجوزات `reserved` الخاصة بالمستخدم الحالي فقط، منفصلة عن الملفات `uploaded`.
- يظهر الحجز غير المكتمل في واجهة البلاغ مع إجراء صريح لإلغائه.
- الإلغاء مسموح فقط لمالك الحجز وفي بلاغ ما زال يسمح بالرفع.
- الإلغاء لا يحذف أي كائن من Storage. إذا وُجد كائن بالفعل على مسار الحجز، تُرفض العملية بـ `ATTACHMENT_OBJECT_PRESENT` ويُطلب إعادة اختيار الملف نفسه لإكمال القراءة والتحقق ثم `finalize`.
- إذا لم يوجد كائن Storage، يُؤرشف الحجز بحالة `cancelled` مع `cancelled_at` و`cancelled_by` و`cancel_reason` بدل حذف السجل.
- الملفات التي أصبحت `uploaded` لا تمر بمسار الإلغاء ولا يمكن حذف أصلها بهذه الوظيفة.
- الحجوزات الملغاة لا تدخل في حد الثمانية، ولا يعاد استخدام UUID الملغى عند اختيار ملف جديد.
- بعد إلغاء حجز ملف ما زال موجودًا في ذاكرة الصفحة، تُمسح علاقة الملف بالحجز السابق حتى يحصل نفس `File` على حجز جديد بدل إعادة محاولة المسار الملغى.
- لا توجد سياسة UPDATE أو DELETE مباشرة للمستخدمين على أصول Storage.

## تطبيق Staging المعزول

طُبقت الترقية على فرع Supabase المعزول `v267-isolated-test` فقط، وليس Production:

- `20260912181410 maintenance_attachment_reservation_abandonment`
- `20260912181849 maintenance_attachment_cancellation_convergence`

ثم نُفذ اختبار PostgreSQL مستضاف داخل `BEGIN ... ROLLBACK` باستخدام عضوية موجودة في Staging وبيانات صناعية داخل المعاملة فقط. أثبت الاختبار:

1. إنشاء `reserved` وظهوره في `pending_reservations`.
2. إلغاء حجز لا يملك كائن Storage وتوثيق المستخدم والسبب.
3. اختفاء الحجز الملغى من القائمة وعدم إعادة استخدام UUID الملغى.
4. إنشاء حجز جديد لنفس المحتوى بمعرّف جديد.
5. رفض الإلغاء عندما توجد بيانات على المسار في Storage مع بقاء الكائن دون حذف.
6. نجاح `finalize` لاحقًا لنفس الحجز المحمي وتحوله إلى `uploaded`.
7. تنفيذ `ROLLBACK` في نهاية الاختبار، لذلك لم تبق بيانات الاختبار الصناعية.

## الأدلة البرمجية

- `staging-database/sql/maintenance-attachments.sql`: قاعدة الحالة والتدقيق ومنع حذف Storage أثناء الإلغاء.
- `staging-database/supabase/migrations/20260912181849_maintenance_attachment_cancellation_convergence.sql`: ترقية قابلة للتطبيق على بيئة V267 المعزولة.
- `src/v267/components/maintenance-attachments.js`: تحقق readback، توثيق الإلغاء، وتحرير الحجز المحلي بعد الإلغاء/الحفظ.
- `src/v267/components/maintenance-attachment-panel.js`: واجهة عربية واضحة للحجوزات ورسالة حماية البيانات الموجودة في Storage.
- `tests/v267-maintenance-reservation-cancel.test.mjs`: يغطي الإلغاء، حد الثمانية، إعادة استخدام نفس `File` بحجز جديد، حماية Storage بعد فقد رد الرفع، منع إلغاء الأصل النهائي، ورفض metadata المزورة.

## حالة CI والقبول

لا يُعد هذا الإصلاح وحده قبولًا نهائيًا للبند أو للإصدار. على أحدث الرؤوس أثناء هذه الجولة، فشلت GitHub Actions قبل تشغيل خطوات الـJobs نفسها؛ ظهر Job بلا خطوات ومن دون Runner مخصص. أُعيد تشغيل Runtime Job واحدة فقط للتحقق من استعادة خدمة التنفيذ، ولا يتم تحويل هذا العائق إلى نجاح اختبارات.

ما يزال مطلوبًا قبل اعتماد الإصدار: نجاح CI على الرأس النهائي نفسه، Preview مطابق وناجح، والاختبار العملي بالحساب الحقيقي على Desktop وiPhone وiPad، إضافة إلى بوابات النسخة الاحتياطية والاستعادة والrollback الشاملة المحددة في Release Gate.

Production وV266 خارج نطاق هذا الإصلاح ولم يتم تعديلهما أو نشر شيء عليهما.
