# سجل تسليم واستلام المستندات — البند 125

أُضيف سجل عملي من شاشة «مستندات الأطراف والعقار والعقد والإخلاء»، تحت كل مستند مرفوع، بزر «سجل تسليم واستلام هذا المستند». قاعدة التنفيذ هي النسخة `411333460945d2ee02351e1bda161346f2f0b2a5` مع الحفاظ على تحديثاتها.

## التنفيذ

- تسجيل المسلّم والمستلم، وقت التسليم بتوقيت الكويت، أصل/نسخة وعدد النسخ، الطريقة والملاحظة، وإثبات تسليم محفوظ ضمن السجل نفسه.
- يُسند مسجّل العملية واسمه ووقت تسجيلها من الخادم. لا يقبل العميل اختيار هوية مسجّل أخرى.
- يحفظ القيد بصمة SHA-256 ورقم وعنوان ووقت رفع كل من المستند الأصلي وإثبات التسليم. لا يغير الملفات أو سجلاتها.
- المستند غير المكتمل أو الإثبات غير المرفوع أو المرتبط بسجل آخر لا يقبل. المستند ذاته لا يُعد إثباتًا لتسليمه.
- القيود الأصلية غير قابلة للتعديل والحذف. الإلغاء سجل مستقل بسبب وهوية ووقت، ويبقى القيد الأصلي ظاهرًا.
- إعادة الطلب بالمعرف نفسه والمحتوى نفسه لا تكرر القيد؛ اختلاف المحتوى يرفض. عند ضياع الرد تتحقق الواجهة من السجل المحفوظ، ولا تعلن النجاح لمجرد نجاح طلب الكتابة.
- القراءة والكتابة تتطلبان عضوية نشطة وصلاحية المستندات وصلاحية السجل/العقار الحالي. لا منح جديدًا لحسابات المستخدمين. الجداول خاصة، مع RLS ومنع الوصول المباشر، وواجهة عامة SECURITY INVOKER تستدعي دالة خاصة محدودة النطاق.

## الفحص المنفذ

1. نجحت 30 حالة JavaScript تشمل 8 حالات لسجل التسليم، والرفع الأصلي، والتحقق من بايتات الرفع واستعادة انقطاعه، وحدود الجلسة. نجحت أيضًا 3 حالات قائمة فحص/عقود تجارية، منها فصل بنود المعاينة على أسطر LF وCRLF؛ هذا الأخير تحقق من سلوك موجود، وليس إصلاحًا جديدًا.
2. أعيدت قاعدة الاختبار محليًا عبر PGlite، وطُبقت الإضافة مرتين، ثم نجح `staging-database/tests/document_handovers.sql`.
3. طُبقت الإضافة على فرع Supabase المعزول `ofgmcsmxmdswlovsckqs` بترقية المنصة **`20260912201126_v267_document_handovers`**، ثم نجح اختبار SQL نفسه هناك.
4. الاختبار المستضاف شمل الحفظ وإعادة القراءة، تكرار الطلب وتعارضه، بصمات الأصل والإثبات، الوقت وهوية المسجّل، الإلغاء وإعادته، منع التعديل والحذف، ورفض الحساب الخارجي والعقار الآخر ومساحة العمل الأخرى والقارئ والاتصال المجهول. تراجعت جميع البيانات الاصطناعية.
5. بعد الاختبار بقي **حساب واحد، ومستندان، وكائنان في Storage** كما قبل الاختبار. بقي جدولا التسليم والإلغاء فارغين. الاختبار أنشأ بيانات تخزين اصطناعية داخل المعاملة فقط؛ لم يرفع ملفات فعلية.
6. أُضيفت مجموعة SQL إلى `Release verification workspace` كفحص مطلوب. لا تنسب نتيجة محلية أو مستضافة إلى GitHub CI.

راجع فحص Supabase الأمني: ملاحظة INFO للجداول الخاصة الجديدة عن تفعيل RLS دون سياسات وصول؛ هذا منع افتراضي مقصود مع سحب جميع منح الأدوار العامة واستعمال RPC مفحوص الصلاحيات. لم تُضف سياسة تسمح بالوصول لتسكيت الملاحظة. [شرح الملاحظة](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)، [إرشادات الدوال والصلاحيات](https://supabase.com/docs/guides/database/functions).

محاولة فتح نموذج الواجهة الاصطناعي المحلي عبر المتصفح أعادت `ERR_BLOCKED_BY_CLIENT`؛ لم يجر تجاوز الحجب، ولا تُنسب لهذه المحاولة نتيجة فحص مرئي. تبقى اختبارات DOM المحلية وSQL المستضافة أدلة منفصلة عن اختبار الحساب الفعلي.

## حدود القبول المتبقية

- الأسماء المسجلة ليست مصادقة مستقلة على هوية المستلم، وإثبات التسليم يراجعه صاحب الصلاحية. لا إرسال بريد أو واتساب، ولا توقيع مولد، ولا إثبات قراءة آلي.
